# Store and one rules function (issue #4) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One SQLite store at `OUTREACH_DB`, created by one command, and one rules module that decides every posting and records size and stage evidence, so every later platform issue (#6, #11 to #17, #21) reads and writes one source of truth.

**Architecture:** A new `outreach/` package at the repo root. `outreach/store` owns the connection (guarded against the live path), the ordered migration runner and migration `0001_initial.sql`; `outreach/install.py` is the only code that creates or migrates a store. `outreach/rules` is pure Python over a TOML config: small modules (title, years, location, sponsorship, eligibility, size) feed one `decide()` call, and `rebuild.py` writes decisions under a ruleset version (hash of config plus rule sources) and reports every posting that flips from shown to hidden. Hiding and ordering are not here (#6).

**Tech Stack:** Python 3.14 from Homebrew (`/opt/homebrew/bin/python3`, SQLite 3.51.2), standard library only (`sqlite3`, `tomllib`, `re`, `unittest`), `uv` for the environment and lock file.

**Spec:** GitHub issue #4; decision record #9 (wins over everything); `docs/superpowers/specs/2026-10-18-outreach-platform-design.md` sections 4, 5, 6, 8 and 14; evidence in `docs/research/2026-10-17-current-system-audit.md` section 2 and `docs/research/2026-10-17-data-lifecycle-and-reliability.md`.

## Global Constraints

- Store path: `OUTREACH_DB`, default `~/Library/Application Support/outreach/outreach.db`. Opening the default path (by any spelling) outside the live checkout is refused through `live_checkout.require_live`. No bypass flag, no environment switch.
- Only `python -m outreach.install` creates a store or applies migrations. Opening never migrates. Migrations are ordered files `NNNN_name.sql`, forward only, one transaction each.
- Every table is `STRICT`. Foreign keys on. `journal_mode=WAL`. Timestamps are canonical UTC text `YYYY-MM-DDTHH:MM:SSZ`; dates are `YYYY-MM-DD`. Both are enforced by CHECK constraints.
- `event`, `import_record`, `linkedin_log` and `evidence` are append-only (triggers refuse UPDATE and DELETE). `posting` rows are never deleted.
- Rules config lives in `outreach/rules/config.toml`. Values pinned by #9 and the design: `max_years_asked = 3`; `graduated = "2026-05"`; a posting requiring graduation in 2027 or current-student status is ineligible; a 2027 start date is not.
- Read results are exactly `"ok"`, `"empty"`, `"error"` (#3). An error never closes anything.
- New code is standard library only in this issue; `pyproject.toml` declares `dependencies = []` and every future dependency must be an exact `==` pin.
- Tests: `uv run python -m unittest discover -s tests -t .` from the repo root. `tests/__init__.py` already points `OUTREACH_DB` at a scratch file; no test may use the live path.
- No part of `outreach/` outside `outreach/rules` classifies titles, locations or sponsorship wording.
- Leave `dashboard/`, `mail/` and `refresh/` code untouched. Do not run `python -m outreach.install` against the live path as part of this issue; the live store is first created in #17 part B.
- No em dashes or en dashes in code comments, messages, docs or commit messages.

## Review Focus

1. `OUTREACH_DB` set to the live path in another spelling (`~/Library/...` with a literal tilde, a symlink to the live folder, a relative path that resolves to it): refused like the default. Test in Task 5.
2. A store path containing a space (`Application Support`): connect and install work (URI quoting). Test in Task 5.
3. A hand value re-entered after a newer hand value (size 50, then 80, then 50 again): the newest hand row wins; evidence de-duplication must never swallow a hand row. Test in Task 4.
4. A posting with an empty body (URL-only page that did not render): a decision is still written, sponsorship `silent`, level from the title only, no crash. Test in Task 14.
5. A pathological body (1 MB of text, repeated "years" and "graduat" words, non-ASCII): `decide()` returns in under 2 seconds (no catastrophic regex backtracking). Test in Task 14.

## Schema: migration 0001

`outreach/store/migrations/0001_initial.sql` is exact copy: the implementer of Task 4 writes this file as below. Page-level settings (`auto_vacuum=INCREMENTAL`, `journal_mode=WAL`) are set by `install` before this file runs, because `auto_vacuum` must precede the first table.

Every timestamp column carries the full CHECK. `x IS strftime(...)` (not `=`) is deliberate: with `=`, an impossible value such as month 13 makes `strftime` return NULL and the CHECK passes; `IS` rejects it and still lets NULL through for nullable columns. Verified on SQLite 3.51.2 on 2026-10-19. Foreign keys may name a table defined further down (SQLite checks them at write time).

```sql
CREATE TABLE schema_migration (
  version    INTEGER PRIMARY KEY,
  name       TEXT NOT NULL,
  applied_at TEXT NOT NULL CHECK (applied_at IS strftime('%Y-%m-%dT%H:%M:%SZ', applied_at))
) STRICT;

CREATE TABLE company (
  company_id    INTEGER PRIMARY KEY,
  name          TEXT NOT NULL CHECK (length(trim(name)) > 0),
  status        TEXT NOT NULL DEFAULT 'candidate'
                CHECK (status IN ('candidate','backlog','working','closed','removed')),
  close_reason  TEXT CHECK (close_reason IN ('referral','interview','no_sponsorship','no_referrals',
                                             'already_hired','not_now','other')),
  remove_reason TEXT,
  status_note   TEXT NOT NULL DEFAULT '',
  status_at     TEXT NOT NULL CHECK (status_at IS strftime('%Y-%m-%dT%H:%M:%SZ', status_at)),
  -- Paused by Devanshu and held by a reply are separate, so a reply never overwrites his pause.
  paused_at     TEXT CHECK (paused_at IS strftime('%Y-%m-%dT%H:%M:%SZ', paused_at)),
  pause_note    TEXT NOT NULL DEFAULT '',
  held_by_touch INTEGER REFERENCES touch(touch_id),
  held_at       TEXT CHECK (held_at IS strftime('%Y-%m-%dT%H:%M:%SZ', held_at)),
  -- A duplicate merged into another company; every read follows it.
  merged_into   INTEGER REFERENCES company(company_id),
  created_at    TEXT NOT NULL CHECK (created_at IS strftime('%Y-%m-%dT%H:%M:%SZ', created_at)),
  revision      INTEGER NOT NULL DEFAULT 1 CHECK (revision >= 1),
  CHECK ((status = 'closed') = (close_reason IS NOT NULL)),
  CHECK ((status = 'removed') = (remove_reason IS NOT NULL AND length(trim(remove_reason)) > 0)),
  CHECK (paused_at IS NULL OR status = 'working'),
  CHECK ((held_by_touch IS NULL) = (held_at IS NULL)),
  CHECK (merged_into IS NULL OR (merged_into <> company_id AND status = 'removed'))
) STRICT;
CREATE INDEX company_merged ON company(merged_into) WHERE merged_into IS NOT NULL;

CREATE TABLE company_alias (
  alias_key  TEXT PRIMARY KEY CHECK (length(alias_key) > 0 AND alias_key = lower(alias_key)),
  company_id INTEGER NOT NULL REFERENCES company(company_id),
  alias      TEXT NOT NULL,
  source     TEXT NOT NULL CHECK (source IN ('name','hand','import','crawl','merge')),
  created_at TEXT NOT NULL CHECK (created_at IS strftime('%Y-%m-%dT%H:%M:%SZ', created_at))
) STRICT;
CREATE INDEX company_alias_company ON company_alias(company_id);
```

```sql
  BEGIN SELECT RAISE(ABORT, 'inbound_message is append-only'); END;

  BEGIN SELECT RAISE(ABORT, 'inbound_message is append-only'); END;

  BEGIN SELECT RAISE(ABORT, 'postings are never deleted; set closed_at and close_reason'); END;

-- A message is born planned or drafted (sent only for imported history); approval is always an UPDATE.
-- A follow-up exists beyond planned only once the first email has gone out.
CREATE TRIGGER message_insert_state BEFORE INSERT ON message
  WHEN NEW.state NOT IN ('planned','drafted','sent')
    OR (NEW.seq > 0 AND NEW.state <> 'planned'
        AND (SELECT first_sent_at FROM touch WHERE touch_id = NEW.touch_id) IS NULL)
  BEGIN SELECT RAISE(ABORT, 'a message starts planned or drafted; a follow-up waits for the first send'); END;

-- Only these state changes exist. sent is final, so a sent message can never be re-drafted and re-sent.
CREATE TRIGGER message_legal_transition BEFORE UPDATE OF state ON message
  WHEN NEW.state <> OLD.state AND (OLD.state || '>' || NEW.state) NOT IN (
    'planned>drafted', 'planned>skipped',
    'drafted>approved', 'drafted>skipped',
    'approved>drafted', 'approved>sending', 'approved>skipped',
    'sending>sent', 'sending>send_unknown',
    'send_unknown>sent', 'send_unknown>failed',
    'failed>approved', 'failed>drafted', 'failed>skipped',
    'skipped>drafted')
  BEGIN SELECT RAISE(ABORT, 'illegal message state change'); END;

CREATE TRIGGER message_followup_waits BEFORE UPDATE OF state ON message
  WHEN NEW.seq > 0 AND OLD.state = 'planned' AND NEW.state <> 'planned'
    AND (SELECT first_sent_at FROM touch WHERE touch_id = NEW.touch_id) IS NULL
  BEGIN SELECT RAISE(ABORT, 'a follow-up leaves planned only after the first email is sent'); END;

-- Once claimed, the text and identity of a message are frozen.
CREATE TRIGGER message_frozen_once_claimed BEFORE UPDATE OF subject, body, seq, touch_id ON message
  WHEN OLD.state IN ('sending','send_unknown','sent')
    AND (NEW.subject IS NOT OLD.subject OR NEW.body IS NOT OLD.body
         OR NEW.seq IS NOT OLD.seq OR NEW.touch_id IS NOT OLD.touch_id)
  BEGIN SELECT RAISE(ABORT, 'a message is frozen once it is claimed for sending'); END;
```

### Views

```sql
-- The value of each fact a company shows: a hand (locked) row wins, and among hand rows the newest wins
-- whatever its confidence; then confirmed over estimate over guess; then the newest.
CREATE VIEW company_fact AS
SELECT evidence_id, company_id, fact, value, num_low, num_high, confidence, locked,
       source_kind, source_ref, quote, posting_id, observed_on, recorded_at
FROM (
  SELECT e.*, ROW_NUMBER() OVER (
           PARTITION BY e.company_id, e.fact
           ORDER BY e.locked DESC,
                    CASE WHEN e.locked = 1 THEN e.recorded_at END DESC,
                    CASE e.confidence WHEN 'confirmed' THEN 0 WHEN 'estimate' THEN 1 ELSE 2 END,
                    e.recorded_at DESC, e.evidence_id DESC) AS rn
  FROM evidence e
) WHERE rn = 1;

-- Decisions under the current ruleset (every open posting has one after a rebuild).
CREATE VIEW current_decision AS
SELECT d.* FROM decision d
JOIN ruleset r ON r.ruleset_version = d.ruleset_version AND r.is_current = 1;

-- One decision per posting: the current one, else the newest kept (closed postings are not re-decided).
CREATE VIEW posting_decision AS
SELECT posting_id, ruleset_version, decided_at, lane, level_tier, level_ok, level_basis, years_asked,
       years_quote, us, sponsorship, sponsorship_quote, citizenship, citizenship_quote, eligibility,
       eligibility_reason, eligibility_quote, start_2027
FROM (
  SELECT d.*, ROW_NUMBER() OVER (
           PARTITION BY d.posting_id
           ORDER BY r.is_current DESC, d.decided_at DESC, d.ruleset_version DESC) AS rn
  FROM decision d JOIN ruleset r ON r.ruleset_version = d.ruleset_version
) WHERE rn = 1;
```

The CHECK lists on `board.ats`, `event.entity`, `evidence.source_kind` and similar enums will grow. In SQLite a changed CHECK means a table rebuild inside a migration (create new, copy, drop, rename), which `migrate` runs in one transaction; plan for that cost rather than loosening the CHECKs.

### Left out on purpose

- **Per-run board fetch rows for every board.** At 36,000 boards they would cost about 33 GB a year (data-lifecycle research, Part A3). `board_read` keeps only the last 10 reads per board, for about 1,000 boards (#21's list), which is what the Needs-you view shows.
- **Posting content history** (Radar's `posting_version`, 77% of radar.db). `posting.body` holds the latest body, which is all a rebuild needs.
- **Full-text search index.** Search over about 1,000 companies and their people is fast with `LIKE`; #11 can add FTS5 in its own migration if it is not.
- **Hide and order columns.** #6 owns them, built on `current_decision`, `company_fact` and `no_go`.
- **An application table.** Applications and pipeline stages are `event` rows (`entity = 'application'` or `'company'`), which is what the design's events row says.
- **A failed attempt's Message-ID column.** When a claim ends `failed`, #14 writes an `event` (`entity 'message'`, `kind 'claim_failed'`, detail with the `pending_rfc_id` and error) before clearing it, so no attempt is lost.
- **LinkedIn invite and note caps.** #9: he handles LinkedIn himself.
- **Retention sweep, backups, monitoring.** Deferred by #7.
- **PhD-only and school-only rules.** The old `final_merge.py:58` dropped PhD-only roles; #9 does not list them as hidden, so the rules do not decide them (open question 2).
- **A `done` company status.** Done means `status = 'closed'` with `close_reason` in (`interview`, `referral`), which is how #12 view 7 defines it.

### The mail state machine, old to new

| `mail/store.py` / `mail/sender.py` | New store |
|---|---|
| `drafted` | `message.state = 'drafted'`, `seq = 0` |
| `approved` | `message.state = 'approved'`, `approved_at` |
| `sending` (claimed, Message-ID saved) | `message.state = 'sending'`, `pending_rfc_id`, `claimed_at`; at most one store-wide (`message_one_sending`); subject and body frozen from here on |
| `send_unknown` | `message.state = 'send_unknown'` (keeps `pending_rfc_id`) |
| reconciled (found or not found in Sent) | `message.reconciled_at` set; state becomes `sent` or `failed` |
| `sent` | `message.state = 'sent'` (final), `rfc_message_id`, `gmail_message_id`, `sent_at`; `touch.first_sent_at`, `first_rfc_id`, `gmail_thread_id` on seq 0 |
| `failed` | `message.state = 'failed'` (safe to approve again); the attempt's Message-ID goes to an event |
| `followup_ready` | a `message` with `seq` 1 to 3 in `planned` or `drafted` whose `due_on` has come |
| `followup_approved`, `followup_sent` | the same `message` row in `approved`, `sent` |
| follow-up numbers, `pendingFollowup` | `message.seq` |
| `replied` | `touch.state = 'replied'`, `replied_at`, `reply_kind` (`unsorted` until he sets interested, not now, said no or asked to stop); the reply itself in `inbound_message` |

Steps, none of which holds the write lock for longer than one batch:
    1. In a short transaction, insert the `ruleset` row if absent, **not current** (`config_toml` = `cfg.raw` decoded). Only then `start_job("rebuild", version)`, so `job_run.ruleset_version` has its row.

ON CONFLICT(posting_id, ruleset_version) DO UPDATE SET` every column). The API and sender (5 s busy timeout) wait at most one batch.
    4. In one short transaction, switch: `UPDATE ruleset SET is_current = 0 WHERE is_current = 1`, then `UPDATE ruleset SET is_current = 1 WHERE ruleset_version = ?` (two statements: one `SET is_current = (ruleset_version = ?)` trips `ruleset_one_current` when going back to an older version).
    5. Prune in batches: delete decision rows whose version is neither current nor the one just replaced, but only for postings that still have a row under one of those two (a closed posting's only decision is kept). About 40 MB per full version is not kept forever.
    6. `finish_job("ok", summary)` with `decided`, `previous`, `pruned` and the three id lists. On any exception: ROLLBACK the open batch, `finish_job("failed", error=...)`, re-raise. ## Where the issues and the design disagreed, and what this plan does

1. **Company status.** Design section 4 lists active, backlog, removed, done, no-go. #11 needs pause, resume, close with a reason and reopen, #15 needs a picked state, and the UI shows "paused" and "held" next to the status. This plan uses `candidate`, `backlog`, `working`, `closed` (with reason), `removed` (with reason), plus `paused_at` (his) and `held_by_touch` (a reply) as separate fields, so a reply never overwrites his pause. Done is `closed` with interview or referral (#12 view 7's own definition); no-go is the `no_go` table, because it also covers people and carries a reason and source.
2. **Domain.** Design section 4 puts domain both on the company row and in evidence. #16 needs domain editable with a source and a lock, like size, so it lives only in `evidence`, read through `company_fact`.
3. **Review triggers.** #16 lists five triggers; design section 5 and #6 also say size guesses raise a review item, and #13's `flag_review` needs one. `review_item.kind` allows the five plus `size_guess` and `flagged`. The UI's labels (`zero_jobs`, `unclear_sponsorship`, `unknown_size`, `missing_domain`) are display names for `board_empty`, `sponsorship_unclear`, `size_unknown`, `domain_missing`.
4. **"Reconciled" as a state.** The brief lists it, but `mail/store.py` has no such state: reconciling is the transition from `sending` or `send_unknown` to `sent` or `failed`. It is `message.reconciled_at`.
5. **Follow-up schedule as an entity.** #4's scope lists it; here it is the three `message` rows (`seq` 1 to 3, `planned`, `due_on`), so a follow-up's schedule, draft and send are one row.
6. **`synchronous`.** The data-lifecycle research recommends NORMAL; this plan uses FULL, as Job Radar does, because a lost commit of a send claim could mean a second send.
7. **Install command.** Design section 14 says `python3 -m outreach.install`; with uv it is `uv run python -m outreach.install`.
8. **Read streaks.** The old `board_status.py` keeps streaks per company; design section 6 and #21 speak of boards. The store keeps them per board.
9. **Undo a LinkedIn log.** The UI says "delete the last step by id"; design section 4 makes history append-only. An undo is a new `linkedin_log` row (`kind 'undo'`, `undoes`), and the API hides the undone step.
10. **Touch states.** The UI lists touch states such as `followup_ready` and `followup_sent`; in the store those are derived from `touch.state` plus the current `message` row (see the state machine table). #11 builds the UI's list.
11. **No-go reasons.** The UI's No-go view lists "removed by you" and "over 300"; removal is a company status (#15), so the API lists removed companies next to `no_go` rows, and `over_300` is a `no_go` reason only when #6 or #17 records one.
