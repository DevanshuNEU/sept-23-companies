# Web app, phase 1 (issue #12) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the real React app for the seven day-one views in `web/`, running against an in-memory fixture client with the same typed interface the FastAPI app (#11) will serve, so Devanshu can click through the whole morning flow before the store and API exist.

**Architecture:** Every view reads and writes through one interface, `OutreachClient` in `web/src/api/client.ts`, whose types live in `web/src/api/types.ts` and mirror the design spec's section 13 and the #4 schema. Phase 1 implements it with `FixtureClient` over data taken from the mockups. Phase 2 swaps in an HTTP client and turns `types.ts` into aliases of the generated `schema.ts`; views import only from `@/api`, and a lint rule enforces it, so the swap touches no view.

**Tech Stack:** Node 20.19.5 (nvm), pnpm 10.28.1, Vite 8, React 19, TypeScript 5.9 strict, Tailwind CSS 4, shadcn/ui (new-york, zinc), Radix, Lucide, React Router 7, TanStack Query 5, TanStack Table 8 and Virtual 3, cmdk, Sonner, Vitest 4 with Testing Library and jsdom, Playwright 1.64 on the installed Google Chrome.

**Spec:** `docs/design/README.md` (the design spec, with section 13 "Data each view needs"), the mockups in `docs/design/*.html` (the look to match), issue #12, and issue #9 (wins over everything). The store under it: branch `store-and-rules-plan`, `docs/superpowers/plans/2026-10-19-store-and-rules.md`, sections "Schema: migration 0001" and "For downstream issues".

## Lead decisions (recorded 2026-10-19; to be added to design section 14 and #9)

1. **#11 speaks camelCase.** The FastAPI models use Pydantic `alias_generator=to_camel` with by-alias output, and the response-only models are named exactly as the interfaces in `types.ts` (`OutboxView`, `OutboxItem`, `TodayView`, ...). The generated `schema.ts` then matches the views field for field.
2. **"Said no" and "Asked to stop" commit at once.** Setting either reply kind writes immediately, because it adds a no-go row and feeds the clean-day rule. Every other reversible action keeps the 8-second delayed commit.
3. **One worktree per build agent; e2e runs serially.** Each parallel agent works in its own git worktree and branch. Group B and D agents run unit tests, lint and typecheck only. One integrator merges branches one at a time and runs Playwright after each merge, because Playwright and the dev server both need port 5173.

## Review Focus

1. **A held or repeated key approves once.** Holding `A`, double clicking Approve, or pressing `A` again while the first approve waits in its undo window gives one approval and one toast. Tests in Task 6 (`ignores key repeat`), Task 8 (`a second action on a pending item queues nothing`) and Task 15 (`approve fires once on key repeat`).
2. **Keys never act behind the focus.** Typing in the editor, or pressing `a` while the Close dialog or the palette is open, never triggers a single-key action. Tests in Task 6 (`single keys are ignored while typing`, `single keys are suspended while a dialog is open`) and Task 15 (`typing a in the body does not approve`).
3. **An undoable write is neither lost nor undone by a refresh.** A pending write commits once when he leaves the view or the page, and a poll that lands inside the window does not flip the row back. Tests in Task 8 (`flushes pending writes on pagehide`, `pagehide then 8 s: commit once`, `a poll inside the window keeps the overlay`).
4. **A refresh does not move what he is looking at.** When polling returns the selected item in a new group, the row stays where it was until the selection moves. Tests in Task 9 (`keeps the selected item in place across a refresh`) and Task 14 (`selected row stays put after it is approved`).
5. **Dates are right across time zones and DST.** "10:42 ET", "Fri Oct 30, 10:02 PT", "Due Fri Nov 13" and "11 days" come from UTC or a calendar date plus a zone; the fixture spans the Nov 1 2026 DST change. Tests in Task 9 (`formats recipient time across the DST change`, `formatDue reads a date as a calendar date`, `ages count calendar days across Nov 1`).

## How the work is run (lead decision 3)

- **Integration branch:** `web-phase-1`, created by the integrator from `ui-design` once this plan is approved. Groups A, C and E run on it directly (they are sequential).
- **Parallel tasks (groups B and D):** each agent gets its own worktree and branch from the current tip of `web-phase-1`: `git worktree add ../web-t<NN> -b web-t<NN>-<slug> web-phase-1`, then `cd ../web-t<NN>/web && pnpm install --frozen-lockfile`. The agent runs only its own unit tests by path, `pnpm lint` and `pnpm typecheck`, and commits only the paths its task lists. It writes its `e2e/<view>.spec.ts` but does not run it.
- **Integrator, after each merge:** `git merge --no-ff web-t<NN>-<slug>`, then in `web/`: `pnpm install --frozen-lockfile && pnpm lint && pnpm typecheck && pnpm test && pnpm e2e`. Before `pnpm e2e`, stop any server on 5173 (Playwright starts its own with `reuseExistingServer: false` and fails loudly if the port is taken). A red run goes back to the task's agent; nothing else merges until it is green.
- **After Tasks 15 and 16 merge:** the integrator adds one line to `docs/README.md` under Current: how to run the app (`cd web && pnpm install && pnpm dev`, then open `http://127.0.0.1:5173`; add `?scenario=hard_block` and the others to see each state), so Devanshu can click through early.

## The seam: `web/src/api/types.ts`

**Rules for #11 (lead decision 1).** Field names here are the wire names: #11 generates them with `to_camel` from its snake_case Python fields. Each `interface` below is a response-only Pydantic model of the same name. No `Record<...>` or dict-shaped fields: a Pydantic dict generates an index signature, which `noUncheckedIndexedAccess` turns into `T | undefined` at every read, so counts are objects with named fields and lists are arrays. Names follow the #4 schema where it has the value; `// derived` marks what the API computes; `// needs #4 0002` marks a column the #4 plan does not have yet.

## Undo and pending writes (Task 8)

- Every reversible action (pick, unpick, backlog, approve, skip, mark ok, log a LinkedIn step, reply kinds other than said no and asked to stop) goes through `usePendingWrite`. It creates the `requestId` at action time, applies its patches to the cached data at once, shows a Sonner toast with Undo, and calls `commit({ requestId })` when the 8-second window ends, when the top-level view changes (the first path segment, not `?sel=`), or on `pagehide` (`commit({ requestId, keepalive: true })`). Undo or `Z` inside the window drops the write.
- **Overlay, not a cache edit.** Patches live in the provider and are applied to every result of `useViewQuery` for their key, including polls and refetch-on-focus that land inside the window, until the refetch after the commit returns. So a poll never flips "Approved" back to "Draft", and pressing `A` again finds the item already approved and queues nothing.
- **After a flush** (route change or `pagehide`), the toast drops its Undo button and reads its `afterCommit` text ("Approved. Press U to withdraw."); `Z` does nothing for it.
- **Immediate writes** (`immediate: true`): said no, asked to stop, and every dialog action (remove, close, no-go, lift, restore, resume) commit at once, still with an optimistic patch and a toast, without Undo.
- **Counts move with the action.** Patches include the `['shell']` key, so sidebar counts ("4 of 5", drafts to review) update at action time, not after the 8 seconds.
- The API needs no undo endpoints. After the window, the opposite action applies (unapprove, unpick).
