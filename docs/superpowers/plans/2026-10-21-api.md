# API and generated types Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A FastAPI app in `outreach/api` on `127.0.0.1:3100` that serves every view the React app needs (the seven day-one views, the pipeline views of #33, health), refuses writes that do not come from its own pages, makes every write idempotent and revision-checked, enforces the #9 approve blocks on the server, generates `web/src/api/schema.ts` from its OpenAPI schema, and is reached from the web app through an `HttpClient` that replaces the `FixtureClient` one view at a time.

**Architecture:** One router module per view in `outreach/api/routers/`, each paired with response models in `outreach/api/models/` named exactly as `web/src/api/types.ts` (camelCase on the wire through one `Wire` base model). Pure logic that the sender, MCP and crawler also need (draft checks, outcome windows, wins, context for touches) lives in stdlib-only packages beside `outreach/store`, so `outreach/api` is the only place with third-party imports. Every write runs inside one `BEGIN IMMEDIATE` transaction that also records its `Idempotency-Key` and response; a request holds no transaction when it ends. The web side adds `web/src/api/http/` (typed through the generated `paths`), a per-view switch (`compose.ts`) and closes the pending-store items N1 to N3.

**Tech Stack:** Python 3.14 (Homebrew), FastAPI, Pydantic v2, uvicorn, httpx (TestClient), all pinned by `uv`; `unittest` with `fastapi.testclient.TestClient`; SQLite STRICT store from #4; TypeScript 5.9, Vitest, `openapi-typescript`, Node 20.19.5, pnpm 10.28.1.

**Spec:** `docs/superpowers/specs/2026-10-18-outreach-platform-design.md` (sections 10, 11, 14); `docs/superpowers/specs/2026-10-20-opportunity-pipeline-design.md` (sections 8 to 11, 16); issue #11 and its 2026-10-21 scope-change comment; #9 including "Decisions, 2026-10-19" (camelCase on the wire, response models named as `types.ts`). ## Global Constraints

- Never open the live store (`~/Library/Application Support/outreach/outreach.db`). Tests use `tests/storetest.fresh_store()`; a worktree always sets `OUTREACH_DB` to a scratch file. Never bind or call ports 3001, 3002, 3011 or 3013; never call the mail API on :3002. The dev port is 3100 in production and `OUTREACH_API_PORT` (default `CONDUCTOR_PORT + 1` in a workspace) everywhere else.
- Claude never approves or sends. Approve exists only as one route in `outreach/api/routers/outbox.py`; nothing in `outreach/mcp`, the sender or the crawler imports `outreach.api` (Task 1 test).
- Third-party imports only inside `outreach/api`. Everything else in `outreach/` stays standard library (`sys.stdlib_module_names`, `outreach`, `live_checkout`).
- camelCase on the wire both ways (Pydantic `alias_generator=to_camel`, by-alias output). Response models are named exactly as `web/src/api/types.ts` (or #33's seam block); fields carry no `Record`/dict types.
- Every write: JSON body, `Idempotency-Key` header (the client's `requestId`), a `revision` where the row has one, an allowed `Origin`. Errors are the envelope `{code, message, checks}`.
- No connection holds a transaction across requests; no network call and no model call happens inside a transaction. Each request opens its own connection inside the endpoint body (not a FastAPI dependency: a sync dependency and its endpoint can run on different threads, and `sqlite3` connections are thread-bound).
- Writers use `INSERT ... ON CONFLICT`, never `INSERT OR IGNORE` or `INSERT OR REPLACE`. Timestamps are canonical UTC `%Y-%m-%dT%H:%M:%SZ`; dates are `date(x)`. The app's day, week (Monday to Sunday) and month are `America/New_York` (`zoneinfo`).
- Hidden only with evidence (#9). The API shows stored decisions and never classifies a posting.
- No em dashes or en dashes in code, comments, docs, UI copy or commit messages. Commit trailer: `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`. Commit steps name their paths; never `git add -A`.

## Review Focus

Failure modes the issue implies that no single endpoint's happy path catches, most likely first. Each has a named test in the owning task.

1. **A repeated write writes once.** A double click, a retry after a network error and the same key from two tabs give one row, one event and one replayed response; the same key with a different body is refused; a refused write (conflict, blocked) stores nothing, so the retry after a refresh works. (Tasks 4, 11, 19.)
2. **A foreign page cannot read or write.** A write with no Origin (curl), a foreign Origin, a rebinding Host, a form-encoded body, or `Sec-Fetch-Site: cross-site` never reaches a handler; a foreign Origin on a GET is refused too. (Task 3.)
3. **Approve decides on current data.** A no-go added, a colleague draft saved, or a company closed after the draft was saved blocks the approve even though the stored `message.checks` still say pass; a banned phrase or an em dash only warns; a stale revision conflicts. (Tasks 17, 19.)
4. **Two tabs and a busy store.** A stale revision changes nothing and says so; an unknown id is 404; a store locked by the sender is a 503 `busy` envelope with `Retry-After`, never a 500, and the idempotency row is not stored. (Task 4.)
5. **Degenerate data never makes a 500.** An empty store, a company with no postings, people or score, rates with a zero denominator, a weekend, a Friday's "tomorrow", a week across the daylight-saving change, a touch with no person. Every GET returns its empty view. (Tasks 6 to 22, each has its empty test.)

## Decisions this plan makes (the issue and the design leave them open)

- **Idempotency** is one table, `api_request(request_id, fingerprint, status, response)`, written in the same transaction as the write. The key is the `Idempotency-Key` header. Only 2xx responses are stored. `event.idempotency_key` for each event the write appends is `"<request_id>:<n>"`, a second guard. `log_touch`'s own key (`plan:<entryId>:request`) is separate: it survives a new request id (a press after the commit landed).
- **One extra migration** (`NNNN_api.sql`, number is the next free one at merge; no test hard-codes it) owned by this plan, so no view task touches the schema: `api_request`, `mx_check`, `linkedin_note`, `win_seen`, `watch_dismissal` (Task 4). Open question 1 asks whether #30 should own `linkedin_note` instead.
- **`PlanRow.entryId` is the `rowid` of `daily_list_entry`** (its primary key is `(list_date, company_id)`). `plan_entry_id(row)` is the only place that knows; a test pins that it survives `PRAGMA incremental_vacuum`. A full `VACUUM` is forbidden by the store plan. If #30 adds an explicit `entry_id`, change that one function.
- **`DailyEntry.revision` and `PlanRow.company.revision` are the company's revision** (as the fixture does); `PlanRow.revision` is the entry's own.
- **The people plan's per-row text** (reason, sources, note facts, apply link, search link) is read from `daily_list_entry.why` JSON with these keys, each optional: `reason`, `reasonSources: [{label, url}]`, `applyUrl`, `searchUrl`, `handoff`, `foundOn: {label, url}`. #15 and #13 write them. One parser, `parse_plan_why`, tolerates missing keys (a row with no reason is built with the lane's default sentence and the flag in `reasonSources == []`). Open question 2.
- **A "Nothing yet" answer** arrives as `kind: 'quiet'` on `POST /api/touches/{id}/outcomes`. Before day 21 it is recorded as a snooze event (`outreach_touch`, kind `prompt_snoozed`) and the outcome stays open; from day 21 it sets `quiet_at`. The prompt asks about a touch at day 7, again 7 days after its first snooze, then never; at day 21 the sweeper sets `quiet_at` (system actor). Open question 3.
- **Win ids** encode the touch and the outcome: `win_id = touch_id * 8 + index(kind)` with kinds `accepted, replied, referred, interview, offer` indexed 0 to 4. `Win.unseen` is "no `win_seen` row". The log (`WinsView.wins`) keeps referred, interview, offer and `replied` with `reply_kind = 'interested'`; an accept or any other human reply appears there only while unseen (that is recognition), and always counts in `counts`. `said_no`, `asked_to_stop` and `auto_reply` are never wins.
- **Funnel counting** is by event date in the period, not by cohort: requests are `linkedin_request` touches with `sent_at` in the period; accepts, replies (any channel, any reply kind except `auto_reply`), referrals and interviews are touches whose own date falls in the period. `FunnelStage.from` is requests for accepts and replies, replies for referrals and interviews. `ProgressPeriod.enough` is `requests >= min_requests` (30). `quiet` is "no accepts and no replies in the period while requests or applications exist". `BaseRates` is all-time over `linkedin_request` touches.
- **Findings** are computed on read from `outreach_touch` (pure function, stable ids from the finding key), the top 2 contrasts of `role kind`, `lane` and `role named` where both groups have at least 20 requests and one rate is at least twice the other. `Finding.changed` and `FindingsView.changes` read `event` rows (`entity 'score'`, kind `weights_changed`, `detail.text`, optional `detail.finding`). Open question 4.
- **Search index cap.** The store will hold about 18,000 companies; one index of all of them is too big for the browser. `SearchIndex.companies` holds companies that are not `candidate`, or have a person or touch, or rank in the top `search_index_top` (3000) by the latest score. Open question 5.
- **Config** for the numbers the API owns is `outreach/api/config.toml`: `[notes] max_chars = 200`; `[outcomes] min_requests = 30, finding_group_min = 20, prompt_after_days = 7, reask_after_days = 7, quiet_after_days = 21`; `[plan] daily_people = 7, linkedin_monthly_limit = 150`; `[search] index_top = 3000`; `[sending] window = ["08:30", "16:30"]`, `ramp = [20, 30, 40, 50, 60, 70, 80, 90, 100]`.
- **Approve** re-runs every check on current data inside its transaction (Task 17), refuses on any `block`, and saves the fresh checks to the message even when it refuses. It moves only `drafted` to `approved`; `failed` to `approved` belongs to the sender (#14).
- **Mail server check** (`no_mail_server`) reads `mx_check` (`ok` or `none`, 24 hour TTL, `unknown` never stored). Approve resolves a stale or missing domain first, outside the transaction, with DNS over HTTPS (urllib). `none` blocks; `unknown` warns (`mail_server_unknown`).

## Task 3: Host, Origin, content-type and Fetch-Metadata guards

**Files:**
- Create: `outreach/api/guards.py`
- Modify: `outreach/api/app.py` (middleware, outermost)
- Test: `tests/test_api_guards.py`

**Interfaces:**
- Consumes: `Settings`, `ApiProblem` envelope (a refusal is `403 forbidden`, built before any router runs; the middleware writes the envelope itself).
- Produces: `GuardMiddleware`: allowed hosts are `127.0.0.1:<port>` and `localhost:<port>`; allowed origins are `http://127.0.0.1:<port>`, `http://localhost:<port>` and `settings.dev_origins`. Rules: (1) a Host not in the set is refused on every method (DNS rebinding); (2) a write method (`POST`, `PUT`, `PATCH`, `DELETE`) must carry an Origin in the set, `Content-Type: application/json` and, when present, `Sec-Fetch-Site: same-origin`; (3) a read carrying an Origin outside the set, or `Sec-Fetch-Site: cross-site`, is refused; (4) the API sends no CORS headers, ever; (5) `OPTIONS` is refused (there is no preflight to answer). Static files obey the Host rule.
