# Needs-you list Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the five Needs-you triggers real. The pipeline raises each one, Devanshu settles each in one click (mark ok, mark no-go with a reason, or set the field with a source), a settled item stays settled until the evidence under it changes, and every settling is either undoable or locked on purpose.

**Architecture:** A standard-library package `outreach/review/` owns raising, sweeping, settling and undoing review items, so there is one place that knows what each item kind means. Three of the five triggers (3, 4, 5) have no producer in any written plan; this plan adds them as a sweep over stored data. Triggers 1 and 2 are raised by the crawler (#21) and only reconciled here. The API (#11 Task 20) and the React view become thin shells over this package. No schema change.

**Tech Stack:** Python 3.14 (Homebrew), standard library only in `outreach/review/`, SQLite STRICT store, `unittest`; React 19, TypeScript, Vitest, Playwright in `web/`.

**Spec:** `docs/superpowers/specs/2026-10-20-opportunity-pipeline-design.md` (sections 5.2 merges, 5.4 size, 7.3 reader disagreements, 8 hide and flag, 16 how it should feel). Issue #16, issue #9 ("Needs-you list" and "Changes, 2026-10-21"), issue #4 (the store). ## Decisions this plan makes (the issue and the design leave them open)

- **"A company he picked" (trigger 4) and "a company he is emailing" (trigger 5) (Pending Devanshu Q8).** Today is now a plan of people, so there is no pick click. In play means a live company (status `candidate`, `backlog` or `working`, not merged, no active no-go) that is `working`, or has an entry on the latest daily list within 4 days with state `picked`, or with a named person and state `proposed` or `picked` (basis `planned`). Emailing means a person with an address at the company has a message in `planned`, `drafted`, `approved`, `sending`, `send_unknown` or `failed` on an open touch, or the latest list has an email row for a person there. - **Items are raised by a sweep over stored data**, not by the code that stores the data. `sweep_needs_you(conn)` is idempotent and cheap, runs every 30 minutes from launchd and at the end of the morning plan, and can run for one company right after a pick or a person is added (Pending Devanshu Q23). There is no `job_run` kind for it (the CHECK has none and a new one would rebuild `job_run`, which `import_record` references). So that a dead sweep is visible in health, every full run appends one heartbeat `event` whether or not anything changed: entity `review_item`, kind `sweep_run`, actor `system`, detail the counts, idempotency key `sweep:<YYYY-MM-DDTHH>:<00 or 30>` (the UTC half hour, `ON CONFLICT DO NOTHING`, so at most one per half hour). #11 Task 6 shows "Needs-you sweep: last run" from the newest one.
- **One helper raises every review item:** `outreach.review.raise_item` (Task 2). #13 calls it with `actor='claude', reopen=False` and #17 with `raised_by='import', actor='import'`; #21 and #6 may keep their inline inserts (same index, same meaning).
- **`raised_by` is provenance by the data read**, from the existing set: `rules` for trigger 3 (a stored decision), `daily_list` for trigger 4 (the plan and picks), `sender` for trigger 5 (queued email). A sweep clears only items of its own `(kind, raised_by)`, so #31's `domain_missing` item (`crawler`) is never cleared by this one.
- **Settled stays settled.** `review_item_once` makes the same key a no-op. This plan adds two rules on top: a company he already decided a `(kind, evidence_key)` for is not asked again on another posting with the same wording; and an item that cleared itself (`cleared`) comes back, reopened, if its condition returns, while one he settled never does.
- **Evidence keys:** trigger 3 `sha256` of the lower-cased, whitespace-collapsed quote, first 16 hex; trigger 4 `no-size`; trigger 5 `no-domain`; triggers 1 and 2 are #21's (`streak_since`). Size and domain items cannot reopen on "changed evidence": the only change is the fact arriving, and that clears them.
- **Scope of trigger 3** (so it cannot flood the list): an open posting, current decision `sponsorship = 'unclear'`, shown by the rules (`passes` with the intern lane counted as engineering), no pending read in `read_queue`, not on a doubtful board, at a live company that is in play or in the top `sponsorship_top_n` (150) of `ranked_list`, with no locked sponsorship fact and no other visible open posting that reads `yes` or `opt_only`. One item per company, on its newest such posting.
- **The five fixes:** `ok` (marked ok, nothing else written); `no_go` (a `no_go` row, `source 'devanshu'`, `source_ref` his source; nothing else changes, and approve and the sender already refuse a company on the list; on an item that names a person, Claude's suggestion, the row is person-level); `edit size|domain|sponsorship` (a locked hand fact); `edit board_url` (replace the board, Task 11); `merge` (Task 9). A fix settles the company's other open items of the same family, and a no-go settles all of its other items, as `cleared`.
- **Undo (Pending Devanshu Q21).** Inside the 8 second window the web pending store's Undo sends nothing (built, tested here for the new fixes). After it, `reopen_item` puts an `ok` or `no_go` item back open (the no-go row is lifted; a lifted row means automation never re-adds it) and a merge is unmerged. A hand edit cannot be taken back: evidence is append-only and a restored value would have to be written as a locked hand row.
- **Reasons for board items are built from live board state** (`queries.display_reason`), because #21 raises `board_empty` on the first empty read and a stored sentence would say "once" after the board closed its postings on the second.
- **`size_unknown` can be raised for most of a plan's rows** (no day-one source has headcount). That is intended: one number from a LinkedIn company page is the design's own answer (5.4), and it comes before he spends a request on a company over 300. It is bounded by the plan's size (up to 60 rows) and by the 14 day stale clear (Task 7).

## Review Focus

Failure modes the issue implies that no single task's happy path catches, most likely first. Each has a named test in the owning task.

1. **A flood.** 12,000 stored postings and 18,000 companies must not become hundreds of items. Only in-play or top-150 companies get an item, one per company, and a re-run adds none. (Tasks 5, 6, 7.)
2. **A settled item comes back.** The same evidence again, the same wording on a new posting, a re-run of every producer, a second tab, a double click: nothing returns, nothing is written twice. A changed key does raise, and says what changed. (Tasks 2, 5, 6, 8, 12, 13.)
3. **Missing input read as "all clear".** A ruleset that is not current, no recent plan, a store with no decisions: the sweep skips and reports why, and clears nothing. (Tasks 6, 7.)
4. **A bad or stale hand value.** `lots` as a size, `gmail.com` or a shared payroll domain as a domain, a stale revision, an edit with no source, the wrong field for the kind: refused with a plain reason, nothing written, item still open. A good value is never overwritten by a later automated row. (Task 8.)
5. **Undo that does not restore.** Undoing a merge must restore status, close reason and his pause exactly; undoing a no-go must not lift a no-go that was already there; a fix never touches a message. (Tasks 8, 9, 10.)

## Task 2: Item helpers

**Files:**
- Create: `outreach/review/items.py`
- Test: `tests/test_review_items.py`

**Interfaces:**
- Consumes: `append_event`, `utcnow` (`outreach.store`), `ReviewError`.
- Produces:
  - `unit(conn)`: a context manager: a write unit that begins `BEGIN IMMEDIATE` when the connection is idle and uses a savepoint inside a caller's transaction (the same pattern as `outreach/rules/rebuild.py::_atomic`; if the controller promotes it to `outreach.store`, this becomes an import).
  - `@dataclass(frozen=True) class Raised: review_id: int; created: bool; reopened: bool; state: str`.
  - `raise_item(conn, *, kind, company_id, reason, evidence_key, raised_by, actor='system', reopen=True, board_id=None, posting_id=None, person_id=None, now=None) -> Raised`: the one helper every plan uses to raise a review item (#13 with `actor='claude', reopen=False`; #17 with `raised_by='import', actor='import'`). `ValueError` when `reason` holds an en or em dash or is blank (callers that pass outside text clean it first with `words.clean`). Inserts with `ON CONFLICT DO NOTHING`; on a conflict looks up the row by the index columns (`ifnull(..., 0)`); a row in state `resolved` with resolution `cleared` is reopened when `reopen` is true (state `open`, resolution NULL, `resolved_at` NULL, note `''`, new reason, `revision + 1`, `reopened=True`) and returned untouched when it is false; any other resolved row is returned untouched (`created=False`, `state='resolved'`). A new row appends `event` (`review_item`, kind `raised`, actor `actor`, key `review-raised:<id>`). With `reopen=False` the helper writes nothing but that insert and its event, so it runs under #13's write guard (insert only, actor `claude`). A CHECK failure is never swallowed.
  - `get_item(conn, review_id) -> sqlite3.Row` (`ReviewError('not_found', ...)`).
