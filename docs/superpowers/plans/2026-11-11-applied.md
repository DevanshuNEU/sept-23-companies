# Applied (#218) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An "Applied" button on every Jobs row records that he applied online to that posting, takes the posting off the job board for good, and lists it on a new Applied page with its job link.

**Architecture:** The write reuses the plan's application shape: one `application` row (company, posting, New York day, the posting's url) plus one `outreach_touch` with channel `application` and an `own` context, so Progress already counts it. The job list hides any posting with a live application touch, next to the passed postings. A new read view `GET /api/applied` lists every live application, newest first; the 330 imported ones show too.

**Tech Stack:** FastAPI + SQLite (`outreach/api`), React + TanStack Query (`web/`), unittest and vitest.

**Spec:** Issue #218 and Devanshu's words (2026-11-11): "Whenever I click on 'I applied online,' that company or that position gets registered. It creates a list ... with their job links ... when I click on 'I applied' then that particular position should leave, go away from the job board."

## Global Constraints

- No em or en dashes in any copy, test name or comment (#9 Writing).
- Applied hides only that posting, never its company, and is not Mark reached: no `company_reached` event, no company status change, no no-go.
- One application per posting: a second Applied on the same posting writes nothing and says when he applied.
- Every write is one `run_write` with the page's `Idempotency-Key`; the same key replays the first answer.
- Tests use scratch stores only (`tests/__init__.py`); no live paths, no network.
- UI through the craft gate (`~/.claude/skills/craft`), matching the Pass and Mark reached patterns on Jobs.

## Rulings made for him (Devanshu can overrule)

- Button label "Applied", key `I` ("I applied"); keys A, X, C unchanged.
- The row leaves at once and the toast offers Undo for the same window as Pass; nothing is sent before the window closes. No undo after that in this version (a follow-up if he asks).
- A closed or no-go posting can still be marked applied: he applied, so it is recorded.
- The Applied page sits under Lists with a count, newest first: role (opens the job link), company (opens the company page), applied day, and "Still open" or "Closed" from the posting.

## Review Focus

1. A posting at a company merged into another: the application and touch go to the survivor (test in Task 1).
2. Double click or a retried request with the same key: one application, one touch (test in Task 1).
3. An applied posting must also stay out of the Higher levels tab and the new-job alerts, not only Your level (test in Task 2).
4. An application whose touch was undone (the plan's undo) must not hide the posting or list on Applied (test in Task 2 and 3).
5. A posting with an empty url: the Applied page shows the title as text, not a dead link (test in Task 5).
